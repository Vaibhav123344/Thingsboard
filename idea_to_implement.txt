Why Chronos-2 is Best for this Task
For a "What-if" scenario like "If raw pressure drops and speed increases, when will vibration peak next week?":
Covariate Intervention: The system can mock/simulate the future values of the known covariates (creating a sequence where pressure drops and speed rises).
Universal In-Context Learning (ICL): Chronos-2 accepts these future covariate tracks as inputs alongside historical target data[2][5]. It models the joint probability space to predict how the target (vibration) will physically respond to those exact conditions over a maximum horizon of 1024 steps[2][3].
Tricky Recurrence Questions (e.g., "If current max temp is 90°C, after how long will it reach that peak again?"): Because Chronos-2 outputs quantile probabilistic forecasts (10th, 50th, 90th percentiles), we can perform precise mathematical peak-finding, cyclic autocorrelation, or wave frequency calculations on the output arrays to determine exact re-occurrence intervals[2].

4. Component 3: Python FastAPI Predictive Sidecar (amazon/chronos-2)
The FastAPI service runs local ML inference using the official chronos-forecasting package[2].
Model Loading: Initialize amazon/chronos-2 (using bfloat16 and CUDA if available; defaults to CPU for lower infrastructure footprint)[2][3].
Intervention Path Builder:
For the future prediction horizon (e.g., 96 steps), generate the baseline covariate tracks (using simple trend extrapolation).
Apply the scale or set rules: decrease the future pressure track array by 20% and step speed to a constant 1500.
Group Attention Packing: Create a multivariate dataset containing:
Target series (vibration): Historical points + padding with NaN for the prediction window[2][6].
Known-Future Covariate 1 (pressure): Historical points + simulated future points[2][6].
Known-Future Covariate 2 (speed): Historical points + simulated future points[2][6].

5. Component 4: Mathematical Feature Extraction (Python)
To allow the AI to answer specific physical peak or recurrence questions, you should perform classic mathematical feature extraction on the predicted output array inside the Python sidecar before sending it to Gemini. This keeps LLM calculations highly accurate.
Task 1: Target Threshold Detection: Search the forecasted array indices to check if the median or p90 upper limit crosses the target value (e.g., 3.5 G-force). Retrieve the exact index and translate it to a predicted UTC timestamp.
Task 2: Peak Finding (scipy.signal.find_peaks): Find local maxima in the future predicted values to pinpoint when the "vibration peak" occurs.
Task 3: Recurrence Analysis: If the user asks about recurrence periods, perform peak-finding over a long sequence, or calculate the mean delta-time between consecutive local maximums:

7. Core Edge Cases to Mitigate in Code
Information Leakage/Scale Mismatch: Telemetry metrics reside on vastly different scales (Vibration is 0–5 Gs, Speed is 0–2000 RPM). Chronos-2 applies internal mean-scaling on input groups, but the data-aligner must handle scaling normalization gracefully.
Missing Covariate History: If a covariate sensor fails temporarily, ThingsBoard will return missing points. The system must use linear interpolation or forward-fill to prevent passing empty or NaN blocks to the prediction network.
Overly Long Prediction Horizon Requests: Chronos-2 maxes out at 1024 prediction steps[2][3]. If the user asks for a prediction too far into the future (e.g., three months out with 1-minute resolution data), the Node.js parser must automatically downsample the history or refuse the command with a warning.
